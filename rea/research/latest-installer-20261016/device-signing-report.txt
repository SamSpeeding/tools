1.0.0.76 对 1.0.0.73：设备、签名、请求故障处理静态对比
日期：2026-10-16
范围：仅 marshal/dis 静态解析；不导入/执行目标模块，不启动签名器，不请求平台。

结论：这次确实新增了视频模型的空响应识别、跨模型接口恢复/探测配合，但没有修改签名器算法/调用、设备池生成/注册方式，也没有因为旧批量 JSON 空而新增切换 baseUrl 的逻辑。新的模型获取顺序由主报告单独说明。

一、签名与设备未改
JAR、libmetasec_ml.so、libc++_shared.so、ms_16777218.bin、devices.json 完全相同；devicepool.pyc、nettls.pyc、downloader.pyc 仅源码编译路径/位置等元数据变化，规范化后全部代码对象相同。
签名仍是 _sign_post_once（hongguo.py 源行355，偏移122–244）POST /sign，提交 url 与 headers；_api_once（源行528，偏移434–506）把 sign 的返回值合并进 headers。_req_headers（源行494）、sign（源行375）、refresh_session（源行437）、build_url（源行482）均未改。app._start_signer（新源行954，偏移4–104）仍用 Java 启动 unidbg-sign.jar / com.hongguo.sign.FqTrace serve。没有在这些调用链加 Python Helios/Medusa 替换。
config.json 仅 base_query.device_id、iid、cdid 更换；设备值完整保留在提取文件，证据只列变更键和哈希。69项 devices.json 不变。load_pool（源行98，偏移6–286）仍优先载入该池；build_url（源行482，偏移4–168）将当前池设备 query 覆盖 base_query。因此正常存在池时，不能把 config 的三个新ID当作“整个默认设备池更新”。
gen_device（源行39）仍本地随机数字 DID/IID + uuid4 CDID；并未新增平台注册。refresh_session（源行437，偏移154–380、608–1086）仍向签名服务 /grab 获取现成请求参数/登录头；不是这版新增的设备注册流程。

二、请求异常与恢复的实际变化
_api_once 新增：SG.check_response 后，对 _VM_PATHS 调 _vm_dead（新源行540–543，偏移884–978）。_VmDead 在模块源行2016、偏移2840–2866 声明继承 ValueError。
_vm_dead（新源行2021）检查 JSON 对象、code==0、data对象；新的 video_tab 路径要求非空 video_model_data，单个模型要求非空 data。批量 data 中每个 vid 内容的检查另由模型解析函数承担。这使此前被当成正常返回的部分空壳响应进入失败处理。
api 的修改主要为取消最后一次失败之后的无用 sleep：登录失效源行572–573偏移270–326；风控源行579–584偏移454–670；请求/ValueError 源行600–601偏移1104–1172。只有 attempt+1<max_retries 才等待。换设备调用依然存在，且最后一次也会调用 rotate_device；并不是新加设备轮换。
api 中备用 host 分支（新源行590–596，偏移848–1046）仍仅 _conn_failure 时触发；备用为 api5-normal-sinfonlineb.fqnovel.com，主为 api5-normal-sinfonlinec.fqnovel.com；非连接错误的模型空响应并不因此换 host。

三、来源失效状态与探测
_source_good（新源行834–836，偏移326–442）扩大恢复条件：之前失败的路径与本次成功路径都在 _VM_PATHS 时，即使不是同一路径，也认定模型能力恢复。
_source_probe（新源行904–907，偏移422–516）对模型路径改走 _vm_alive(body,extra)，其余路径仍走 api(...,max_retries=1,timeout=15)。新多路径模型探测由主报告给出顺序。
_source_strike、_source_down、_probe_verdict、SG.check_response 本身未改。SOURCE_BAD_N/SOURCE_BAD_S 仍为2/60（60秒内两次累计失败），SOURCE_RETEST_S=60、LONG=120、LONG_AFTER=600、TICK=5、PROBE_GAP=10。新模型调度会向这套既有机制汇报失败；不是换了签名规则。

证据与边界
结构化证据：device-signing-evidence.json，含原/新文件SHA256、规范化代码对比、函数源行及逐条字节码偏移。
原/新源码文件名分别带 installer\_stage 与 installer\_stage76；不能仅凭 pyc 文件hash不同断言逻辑改变。
静态证据能确认实现适配，不能确认现网稳定成功；未运行原程序/签名器，未访问平台。平台服务端策略和环境变量覆盖不在本项证据范围。
