统一入口与缓存
--------------
get_video_urls 改为复用 get_video_tracks；offline_dl._video_model 也改成
H.get_video_tracks([vid])，再包回 {video_list: tracks}。
因此从下载或原有单集播放入口进入，也会走同一批量优先策略，即使只给 1 个 VID。
get_video_tracks 先去重、查缓存，只对未缓存 VID 调 _vm_lookup。
批大小限制为 1..5；force=True 绕过缓存读取。
缓存 TTL 从固定上限延伸为结合条目 expire_time 计算：
  min(18000 秒, expire_time - 当前时间 - 600 秒)
缺少/无效 expiry 时回到 18000 秒；计算 TTL <= 0 不写缓存。
新模型解析同时支持 video_model 已经是对象或 JSON 字符串。
证据：_vm_entry 2051、_vm_ttl 2065、get_video_tracks 2198；
offline_dl._video_model 1667。源行来自 pyc，不是恢复的原始源码。

故障响应、恢复与签名
------------------
_api_once 在原 SG.check_response 后新增 _vm_dead，检查三类模型响应：
code 必须为数值 0、data 必须是对象；新 tab 必须有非空 video_model_data；
单集 data 不能为空。不符合则抛 _VmDead(ValueError)，不能计作正常成功。
模型路径从通用 _STRIKE_PATHS 分离；旧批量和单集都出现可分类失败时，
_vm_lookup 才调用 _source_strike，避免旧批量一失败就误判整个取流能力不可用。
恢复探测 _source_probe 改用 _vm_alive，多入口探测；_source_good 对模型入口
允许跨路径确认恢复。api 重试最后一轮失败后不再多睡一段退避时间。
详细函数证据与限制见 device-signing-report.txt / device-signing-evidence.json。

JAR、libmetasec_ml.so、libc++_shared.so、ms_16777218.bin、devices.json
字节一致；devicepool 与 nettls 没有去除构建信息后的逻辑变化。
sign、签名请求封装、_req_headers、build_url 与设备刷新核心未更新。
config.json 只改基础 device_id/iid/cdid；默认设备池会覆盖这三个字段。
因此没有观察到类似我们项目“替换 Helios/Medusa”的修复。

离线回放结果
------------
运行 replay_model_functions.py：仅实例化已审阅的模型函数代码对象，
不执行目标模块顶层；api、缓存、时钟均为内存假实现，实际网络请求为 0。
输入 6 个未缓存的合成 VID，以下为逻辑 api() 调用次数，不含通用 API 重试：

  1.0.0.73，成功：单集 6 次；重复调用命中缓存为 0 次。
  1.0.0.76，新批量成功：新批量 2 次（5+1），返回 6 集；重复 0 次。
  1.0.0.76，新批量失败、旧批量成功：新批量 2 + 旧批量 2 = 4 次。
  1.0.0.76，两类批量失败、单集成功：新批量 2 + 旧批量 1 + 单集 6 = 9 次。
  1.0.0.76，新批量各漏一条：新批量 2 + 旧批量 1，补齐 6 集。
  1.0.0.76，新批量模型 JSON 损坏：新批量 2 + 旧批量 2，补齐 6 集。
  1.0.0.76，三路均失败：2 + 1 + 1 = 4 次，调用故障计数后抛出异常。
  1.0.0.76，证书异常：第 1 次就停止，不掩盖证书问题继续回退。
  1.0.0.76，过期模型：返回当前取得 tracks，但不写过期缓存。

共 12 组场景/入口组合通过，完整请求及返回摘要在：
evidence/model-functions-offline-replay.json

边界案例：_vm_entry 对存在条目但缺 video_model/空 video_list 返回 None，
不会抛 _VmDead。_vm_tab_pass 会把 None 写入 out 而不加入回退队列。
合成“新批量每个条目都是空 tracks”时，只调用新批量 2 次，最后返回 0 集。
所以这版增强了适配，但“所有空模型都能继续回退”仍不成立。
这是有限合成场景的行为观察，不表示平台一定会发出这种响应。
