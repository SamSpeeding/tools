# Helios / Medusa 差异与原设备批量稳定性实验

日期：2026-10-14，Asia/Shanghai。承接 [上一轮实验](../batch-model-20261014/README.md)。本轮只做隔离研究，应用代码、配置、vendor、原参考脚本和冻结 `analysis/` 未修改。

## 结论

**Helios 已定位到具体字段差异，并取得受控请求证据；Medusa 确认不是同一个格式版本，JAR v4 内层仍未还原。** 原设备在成功组合下可以连续跨集、跨剧、一次传多个 VID，并不要求每次换设备。

本轮 41 个 HTTP 请求包括 2 个剧详情、38 个批量模型、1 个单模型控制。正常候选组合的 28 次检查全部成功，覆盖两部剧、12 个不同 VID、每次最多 5 个 VID。单独改变 Helios 字段的实验及原 JAR 失败控制另列，不混进这个分母。模型观察窗口为 **10:35:04–10:42:40，约 7 分 36 秒**；不能据此承诺跨天稳定。

## Helios 究竟差在哪里

解密并重新加密逐字节校验，得到：

| 项目 | 原 JAR | 参考 Python 默认实现 |
|---|---|---|
| 明文 | `khronos-1611921764-3019` | `khronos-1588093228-8662` |
| 第二位置，按参考实现命名为 license ID | `1611921764` | `1588093228` |
| 第三位置，按参考实现命名为 App ID | `3019` | `8662` |
| 外部 URL 的 aid | `8662` | `8662` |
| 本样本可验证的 key 派生后缀 | `8662` | `8662` |

这里的 license ID 是平台签名协议的字段，与下载器作者的收费激活码无关。JAR native 内部变量名、3019 的产品归属，没有用猜测补齐。

**不能把明文 App ID 与 key 派生使用的字符串混为一谈。** 两份头均可用同一派生方式正确解密、去 padding，再重新加密还原全部原始 bytes；差异不是普通随机数变化。

更关键的是在线单变量验证。第 09 组在同一批 5 个 VID 上，固定 URL、body、其他所有 headers、时间戳、Helios 随机前缀，只改其明文位置值：

| 顺序 | license ID | 明文 App ID | 结果 |
|---:|---|---|---|
| 1 | JAR 值 `1611921764` | `8662` | `110001`，0/5 |
| 2 | `1588093228` | `8662` | 成功，5/5 |
| 3 | `1588093228` | JAR 值 `3019` | 成功，5/5 |
| 4 | JAR 值 `1611921764` | JAR 值 `3019` | `110001`，0/5 |
| 5 | `1588093228` | `8662` | 重放第 2 条原签名，成功，5/5 |

因此，**在这组请求及 Medusa v3 组合下，license ID 的变化足以让成功变失败；仅明文 App ID 不一致没有触发失败。** 这是比“看见 aid 不一致便认定根因”更强、更窄的结论。它不声明平台所有接口都使用同一验证规则，也不证明 Helios 是唯一问题。

第 08 组使用每次正常重算的签名也得到相同方向的结果，随后第 09 组消除了随机数与时间戳的变化。[字段实验](08-helios-field-isolation.json)、[严格单变量实验](09-exact-helios-counterfactual.json)、[实验代码](run_exact_helios.py)。

## Medusa 已确认什么，尚未确认什么

| 项目 | 原 JAR | 参考 Python |
|---|---|---|
| 去除 khronos XOR 后的外层版本 | `4` | `3` |
| 外层 16 字节标识 | `126f8075e685b236b8eb84ca22cb43e8` | `f7e85ffad7d7dc3bd62ac87057cf6118` |
| 外层 flag | `256` | `256` |
| 内层 protobuf | 未还原 | 已解出并完成整包回环 |
| 与请求的字段绑定 | 内层未知 | 已核对 aid、设备、App 版本、query、body、时间 |

Python v3 解出的真实内容包括顶层和嵌套设备 ID、aid=8662、license=1588093228、App 版本 7.2.9.32、SDK `v04.06.04-ml-android` / `67503104`，以及 PID、环境版本和设备采样字段。设备/应用信息不只出现在 URL 中，也进入了签名内文。

离线核对了原始 query 的 SM3、body MD5、query/body/time 组合摘要、内外设备 ID 和两份时间戳等 11 项绑定。解码后重新加密能逐字节恢复原签名，避免把解析出的偶然字符串当作有效结果。参考脚本的固定环境采样值仍存在；通过这些请求不代表环境采样真实或设备生命周期完整。

**正确 Python Helios + 原 JAR Medusa 仍失败；恢复 Python Medusa 又成功。** 这证明只改 Helios 尚不足以恢复受测组合。但不能说“v4 本身无效”：其内部 aid/license/device、派生密钥、具体算法尚未解开，当前 v3 解码器不适用于它。

详见 [离线解码报告](decoder/README.md)、[候选签名审计](decoder/capture-audit.json)、[实际发出请求审计](decoder/sent-request-audit.json)。完整签名及设备字段仅存在私有文件中。

## 原 JAR 为什么可能带着另一套上下文

实际入口是 `FqTrace serve`，将 URL、headers 直接交给 SO 的 `0x168c80`。Java 层没有把 URL 中的 aid、license、DID、iid 拆开同步进一份 SDK Config 的逻辑，也没有调用同 JAR 里另一类的 `MetasecSign.driveInit`。

其模拟包名、部分 JNI 版本回调固定，与外部请求档案不一致；但 SO 收到完整 URL，仍可能自行解析参数。不能把“Java 没设置”写成“SO 完全不读取”。Helios 实际输出的身份差异已经由解码确认，而这些值在 native 内部如何初始化仍未知。[Java 调用链与边界](jar-context.md)。
