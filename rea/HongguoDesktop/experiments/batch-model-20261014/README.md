# 批量视频模型：隔离实验结论

日期：2026-10-14，Asia/Shanghai。实验时间 10:06–10:25。同一台 Mac、同一网络、同一个目标 VID。研究范围是找规律；未接入应用，未替换生产签名、设备或配置。

## 当前结论

**最强证据指向 `x-helios` / `x-medusa` 这对签名头及其上下文，而不是 JSON 存储格式。** 保留我们的请求档案、原设备池第 0 条 DID/IID/CDID、原 JAR 输出的其他签名头，只把这两个头一起改为所研究脚本的计算结果，批量接口连续两次返回有效模型。单独换 Medusa 在先前实验中未恢复；把 Python 方案中的 Helios 或 Medusa 单独换回 JAR 版本也失败。

**固定原设备可以反复成功，随机新设备不能与它等同。** 原设备配 Python 签名在 10:14、10:24 和 10:25 多次成功，10:25 的原设备五次批量连续验证全部成功（含两次混合签名、一次 curl_cffi）。与之相反，多组随机 ID 出现首次成功、紧接着失败；其中一组原脚本随机 ID 间隔约 8 分 11 秒后仍失败。因此不能再概括成“所有设备都只能成功一次”或“每次必须换 ID”。

这还不是长期稳定性或完整根因证明：没有解出服务端的拒绝判定，也未定位到签名内部某个确切字段。成对签名之间的密钥/上下文关联、模拟环境一致性和真实设备来源仍需进一步区分。

## 最有判别力的结果

| 条件 | 结果 | 可以说明什么 |
|---|---|---|
| 我们原请求 + 原设备 + 原 JAR 批量 | 失败，`110001` | 复现原问题 |
| 同一原设备 + 我们请求档案 + Python 签名 | 多次成功，含间隔与连续请求 | 固定保存的这组身份及请求档案并非必然不可用 |
| 同一原设备 + JAR 其余头 + Python Helios、Medusa | 连续 2 次成功 | 无须整体替换全部签名头就能改变结果，信号集中在这一对 |
| 新随机设备 + JAR 其余头 + Python Helios、Medusa | 两组首次成功；一组立即重试失败 | 成对替换有可重复信号，但随机身份另有复用问题 |
| JAR 方案只换 Python Medusa | 失败 | 单改 Medusa 尚不足以恢复 |
| Python 方案换回 JAR Helios，或换回 JAR Medusa | 失败 | 混用这对头的单项出现不兼容，不能据此指认某一个算法独立错误 |
| Python 方案使用 JAR Gorgon，或 Argus/Ladon，或 Neptune/Soter | 各组首次成功 | 这些项各自可与成功的 Python 组合共存 |
| 我们的 c 域名、7.2.9.32、类型键 `1`、原业务 body | 可以成功 | 不需要先改成脚本的 b 域名、版本或 `1004` 才能成功 |
| requests / curl_cffi | 均成功，原设备 curl 也成功 | 当前 HTTP 客户端不是必要障碍 |
| 16 位 / 18 位新实验 ID | 均有首次成功 | 单凭位数不能解释失败 |
| 固定脚本签名内 PID / launch_time | 首次成功，重复失败 | 仅固定这两个字段未解决随机设备复用 |
| 原设备 + 原 JAR 单个 `video_model` | 三次控制均成功 | 失败并非所有视频模型能力一概不可用 |

成功均为取得目标 VID、5 档轨道及有效格式的下载 URL，画质为 360p/480p/540p/720p/1080p；不是仅以 HTTP 200 判断。本轮没有下载媒体，不等于对这些新 URL 完成了播放验证。

逐请求查看 [CASES.md](CASES.md)，汇总见 [results-summary.json](results-summary.json)。核心实验实现 [lab.py](lab.py)，最后两组为 [run_helios_medusa.py](run_helios_medusa.py)、[run_stored_identity.py](run_stored_identity.py)。

每次请求重新生成时间和签名，body MD5 在发送前校验。普通档案、body 与 ID 按实验分组控制；混合签名时两实现的 `x-khronos` 要求一致。所谓“只换两个头”指同一请求模板上仅覆盖这两个字段，其他 JAR 输出保留；不同请求之间仍有应正常更新的时间、随机签名，不冒充所有原始字节完全相同的重放。

每次请求间隔至少 2.5 秒，只请求两个已有官方模型路径，不自动重试、不注册、不下载媒体。原脚本随机生成的 ID 仅是本地实验数字，未宣称它们已被平台注册。请求顺序已记录；随机身份可能受前次调用影响，所以第 02 组的“JAR 先失败、Python 后失败”不能解释为 Python 签名永远无效。

`private/` 保留完整 URL、headers、body、响应、部分混合签名的两份候选，文件权限 0600、目录 0700。公开摘要只显示设备 hash，不复制原值。前几组摘要最初未收录 Neptune/Soter、画质位于嵌套 video_meta 后补齐；[summarize_results.py](summarize_results.py) 只从原始记录重新派生这些展示字段，未更改原始响应、stdout log 或成功判定。

## 固定 JSON 到底有没有问题

JSON 本身适合持久化配置和身份。应用每次会重新算时间、body MD5 与签名，不是在重复发送一份过期的完整请求 JSON。原设备在本轮多次成功，是直接的反证。

需要改进的是**字段生命周期和来源建模**：协议/版本档案可以配置保存；设备身份应持久且有关联来源；会话材料要按有效期管理；时间和请求签名应逐次计算。当前随包设备池从哪里取得、何时失效、如何正规刷新尚未完整确认；这是一项独立的架构局限，不应直接等同于本次 `110001` 根因。

详见 [固定 JSON 与代码静态研究](../../docs/evidence/batch-config-research-20261014.md)。原 JAR 有固定模拟环境，外层配置与模拟环境并非统一来源，但目前不能仅靠静态版本差异判断到底哪个环境字段被服务端拒绝。

## 新版原程序提供的旁证

中途按用户要求暂停，分析用户提供的 1.0.0.73 安装包，确认作者直接把三个模型入口由批量改为单个，JAR/SO/69 条设备池不变。根据用户后续指示，确认它未展示批量恢复方案后，继续了第 05、06 组实验。[新版逆向报告](../../../research/latest-installer-20261014/README.md)。

这个改动说明新版使用另一接口处理下载，不能证明平台批量整体失效；本轮已观察到批量成功。也不能据此证明作者采用单个接口的具体动机。

## 边界与下一步

已确认：能稳定复现受测组合间的明显差异；原有固定设备在短时连续请求中可用；成对 Helios/Medusa 替换有强信号。没有证据要求我们先重写配置存储或每次生成新设备。

仍未验证：同一批量请求传多个 VID、其他剧集、长时间和多日稳定性、更多原设备；两种签名的内部字段差异；真实设备生命周期；服务端是否有其他维度的限流。不能宣布已彻底修复、IP 风控不存在，或所有随机 ID 永久一次性。

后续最有价值的方向是对照这对签名的结构与环境输入，再用持久原身份验证多 VID 和跨集请求。当前结果足够确定研究方向，本轮在 45 次请求后结束，避免继续堆叠低信息量的随机换设备尝试。

所有阶段保护 hash 相同，并已与当前文件复验：应用 backend/src、config/devices、解密 Python 和原第三方脚本未修改。旧 `analysis/`、CLI 和当前 release app 均未因本轮研究调整；新包材料保存在独立 research 目录，实验材料保存在本目录。
